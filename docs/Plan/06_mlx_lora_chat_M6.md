# M6：MLX-LM LoRA、中文對話評測與端到端延遲 v1.0

> 日期：2026-10-17（時間皆為 Asia/Taipei）｜機器：MacBook Pro M1 Max 64GB，macOS 15.3.1｜目錄：`docs/Plan/m6/`（`tools/` 腳本、`raw/` 原始輸出）
> 限制：不使用 llama.cpp／GGUF；未修改 `src/gemma`、`weights/`。M6 沒有改 `src/gemma-qat` 的程式碼，所以沒有開 `m6` 分支。

## 1. 結論摘要

- **MLX-LM LoRA 這次能訓練，但 Metal 錯誤還是會出現。** 第 1 次跑到 iter 300（約 24 分鐘）時出現 `[METAL] Command buffer execution failed: Internal Error (0000000e)`。依規則重試 1 次：seq 512→384、`mx.set_cache_limit(4GB)`，並從 iter 300 接續（cosine LR 曲線也接著走）。第 2 次在第 400 iter 後又出現同樣錯誤，所以依規則停止。最後的 adapter 是 global iter 400，約 **18.1 萬 tokens**，**沒有達到 0.5–1M 的目標**。
- **沒有 QAT 的 LoRA，snap 回官方 Q4 32-block 網格的損失很大。** 融合後的 bf16 PPL 是 13.15／24.30，snap 成 g32 exact 後變成 **27.28／33.57**；改用 MLX g64 affine（有 bias）則是 13.27／25.20，大小 2.60GB。M5 的 JAX LoRA-QAT 訓練時就在網格上，snap 幾乎沒有損失（13.43／22.68）。**可合併的 LoRA-QAT（M5）仍是最適合 g32 exact 的做法。**
- **PPL 大降主要是因為模型被拉回「語言模型」狀態。** 在對話評測中，三個模型在思考開時幾乎打平（25 題：知識 6/8、指令 6/7）。M5 在思考關時重複和幻覺較多（rep4>0.3 有 10 題，例如把台灣最高峰答成「太魯閣山 3,999 公尺」）。**對話用途中沒有任何模型明顯贏過官方 QAT。**
- **這個 E2B QAT 檢查點實際上沒辦法關閉思考。** 即使模板裡沒有 `<|think|>`，49/50 題仍會自己輸出 `<|channel>thought`。預先填入空的 thought 區塊後，推理內容（多半是英文）會漏到答案裡，造成指令遵循只有 3–4/15、撞上 256 token 上限 25–29 題。
- **「flash」等級延遲最有效的槓桿是限制思考長度。** 官方模型自然思考時，首個答案 token 的 median／P90 是 8.2／14.4 秒。限制思考 128 tokens 後降到 **3.1／3.4 秒**，25 題的品質沒有下降（知識 6/8、指令 6/7、垃圾題 3/5）。Prompt cache 重用能讓約 400 token 系統提示的 TTFT 從 0.19 秒降到 **0.08 秒**。
- **速度量測有背景干擾。** M6 量測時 Chrome Helper 和 LINE 各佔約 100% CPU，decode 只有 44–53 tok/s，大約是 M5 乾淨量測（112 tok/s）的一半。因此各模型間只能做相對比較；絕對秒數在乾淨系統上預估約為一半。

## 2. 執行內容

1. **處理程序檢查：** 只有一個不屬於本專案的 `preview_ui.py`（約 10MB），沒有動它，也沒有其他重度 python 或訓練程序；記憶體空閒 92%。
2. **MLX LoRA：**
   - 設定檔：`tools/m6_mlx_lora.yaml`；wrapper：`tools/m6_mlx_lora_run.py`，支援 resume、`CACHE_GB`／`MEM_GB`／`BATCH`／`SEQ`，並接續 cosine 曲線。
   - 底座：`out/m5/qat-text-hf`（官方 QAT 的 bf16 純文字版）。M5 時 QLoRA 用 g32 量化底座會 Metal crash，所以這次用 bf16 底座。
   - 資料：沿用 M5 的 `m5/raw/mlx_data`，內容是 wikitext-2 train 加 zh-TW 維基百科（`zetavg/zh-tw-wikipedia`，CC BY-SA 4.0；M0 評測文章已排除），每段 512 token，開頭是 BOS。
   - 參數：LoRA rank 16、scale 2，套在全部層的 q/k/v/o/gate/up/down；可訓練參數 24.2M（0.52%）；batch 1；lr 5e-5，warmup 50 後 cosine 降到 5e-6；每 100 iter 存一次檔；開啟 gradient checkpointing。
   - 第 1 次：19:15–19:39，iter 300 後出現 Metal 錯誤（`raw/mlx_lora_run1_metal_error_iter300.log`）。
   - 第 2 次（重試）：19:39–約 19:47，seq 384、cache limit 4GB，iter 100（global 400）後再次出現 Metal 錯誤（`raw/mlx_lora_run2_retry_metal_error_iter400.log`）。
   - Loss：val 3.974（iter 1，seq 512）→ 2.635（iter 250）；第 2 次的 val 是 2.542（seq 384）；train 3.40 → 2.47。訓練吞吐量從 242 tok/s 一路掉到 116 tok/s，可能和記憶體或 cache 增長有關。
3. **融合與打包：**
   - `mlx_lm fuse` → `out/m6/mlxlora-fused`（bf16，8.7GB）。
   - `tools/mlx_exact_grid.py --snap` → `out/m6/mlx-mlxlora-g32exact`：278 個 tensor、1.446 億個 block 全部在網格上，**磁碟 2.7GB，參數 2.89GB，小於 3GB ✓**。
   - g64 affine → `out/m6/mlx-mlxlora-g64`：**2.5GB，參數 2.60GB ✓**。
4. **評測：**
   - `tools/m6_chat_prompts.py`：50 題固定 zh-TW 題目，包含知識 15、指令 15、繁簡字 10、垃圾或不可答 10。
   - `tools/m6_latency.py`：同時量延遲並保存答案。
   - `tools/m6_grade.py`：計算自動指標。
   - `tools/m6_lever_prompt_cache.py`：測 prompt cache 槓桿。
   - `tools/m6_post.sh`：可續跑的整條管線；每一步若已有輸出就跳過。
   - `tools/m6_progress.sh`：Terminal 進度條，並寫入 `out/m6/STATUS.txt`。
   - 第一版 chat eval 因為模型會自己思考、在 256 token 內都還在想，結果無效，已移到 `raw/invalid_natural_think/` 留存。

### 評測方法

- **生成方式：** greedy；使用 chat template，只有 user 一則訊息。
- **思考關：** `enable_thinking=False`，再預填空的 `<|channel>thought\n<channel|>`，上限 256 tokens。
- **思考開：** 加上 `<|think|>`，取偶數題共 25 題，上限 1024 tokens。
- **兩次 run：** 同一個 process 連跑兩輪。run 1 的第 1 題算 cold（剛載入、Metal kernel 第一次編譯）；median 和 P90 只統計 warm 的題目。
- **TTFT：** 從呼叫開始到第 1 個 token，包含 prefill。
- **思考時間：** 從第 1 個 token 到 `<channel|>`（id 101）。
- **TTFA：** 第 1 個答案 token 出現的時間。
- **繁簡字判定：** 用 OpenCC 的 t2s／s2tw 逐字判定；台、吃、粽、峰、里等臺灣常用字列入白名單，否則 s2t 會把它們誤判成簡體字。
- **rep4：** 4 字元 n-gram 的重複率。
- **自動判分項目：**
  - 知識題：比對關鍵字。
  - 指令題：檢查條列數、純數字、字數上限、英文比例、JSON 能否解析等。
  - 垃圾題：答案是否出現拒答或請求澄清的用語。

## 5. 達到「flash」等級延遲的槓桿

| 槓桿 | 狀態 | 實測／判斷 |
|---|---|---|
| **限制思考長度**（思考到 N tokens 時強制插入 `<channel|>`） | ✅ 已實測 | 官方模型（25 題）TTFA median 從 8.21 秒降到 **3.12 秒**（上限 128）／5.83 秒（上限 256）；品質 6/8、6/7、3/5 不變。上限 128 的副作用：答案變長（平均 243→404 字），P90 總時間沒有改善，建議同時限制答案長度。目前做法在強制收尾時會重新 prefill 一次；改用 logits processor 就能省掉。**這是最大的槓桿。** |
| **Prompt／KV cache 重用**（固定系統提示先 prefill，之後每題 deepcopy） | ✅ 已實測 | 約 397 token 的 prompt 中有 383 token 共用前綴：TTFT median 0.191→**0.080 秒**，max 1.54→0.48 秒；前綴建置只需 0.33 秒，且只做一次。多輪對話沿用同一個 cache 也是同一原理。 |
| **量化 KV cache**（`kv_bits` 8／4） | ✅ 已實測，無效 | TTFT 和 decode 都和 bf16 KV 相同，品質逐題也一樣。原因是 mlx_lm 的 `quantized_kv_start` 預設為 5000，短對話根本不會開始量化 KV。只有長上下文（>5k）才有意義，主要效果是省記憶體，不是加速。 |
| **group size g64 vs g32** | ✅ 已實測 | 有背景負載時，g64 的 decode 是 48.8 vs 45.3 tok/s（約 +8%），TTFT 差不多。但 M0／M5 乾淨量測是 g32 exact 112 tok/s、g64 85 tok/s，方向相反，差異和雜訊同一個量級。g32 exact 的 PPL 較好（47.2 vs 48.7），**建議維持 g32 exact**。 |
| **思考關（空 thought 預填）** | ✅ 已實測，這個檢查點不適用 | TTFA 0.09 秒，但推理會漏進答案，指令遵循只有 3–4/15。要真正支援「不思考」，需要在 SFT 或 LoRA 階段用「空 thought 加上直接回答」的對話資料訓練（M7 候選）。 |
| **推測解碼**（speculative decoding） | ⛔ 未實測 | mlx_lm 0.32 支援 `draft_model`，但需要同一個 tokenizer 的更小模型；E2B 已經是 Gemma 4 最小的型號，沒有可用的 draft。可行的替代方案是 prompt-lookup 或 n-gram 自推測：對中文答案重複引用題目的情況有幫助，但需要自己實作。 |
| **mx.compile** | ⛔ 未實測 | mlx_lm 的 `generate_step` 沒有編譯整個 decode step。KV cache 長度會變動，要編譯得處理固定 shape。decode 本質上受記憶體頻寬限制：M1 Max 約 400GB/s ÷ 每個 token 讀取約 2.9GB 權重，上限約 130–140 tok/s，乾淨量測已有 112 tok/s，剩下的空間有限。 |
| **背景負載** | 觀察到 | 關掉吃 GPU／CPU 的程式（這次是 Chrome Helper、LINE）就能讓 decode 速度約翻倍（約 45→約 110 tok/s），這是最便宜的槓桿。 |

**建議的 flash 設定**（官方 QAT g32 exact，2.89GB）：思考上限 128、固定系統提示用 prompt cache、限制答案 max tokens，並在乾淨系統上執行。預估首個答案 token 約 1.3–1.5 秒（換算自本次有負載的 3.1 秒 × 約 0.45），短答案總時間約 2 秒。

## 6. 最佳模型

- **只看 PPL 和大小：** M5 JAX LoRA-QAT g32 exact，2.89GB，PPL 13.43／22.68。
- **對話用途：** 官方 QAT g32 exact，因為 LoRA 版本在思考開時沒有贏，思考關時 M5 的重複和幻覺還比較多。
- **M6 MLX LoRA：** g32 exact 因為 snap 損失不推薦。g64（2.60GB，13.27／25.20）是不需要 JAX 的替代方案，但沒有跑對話評測。

## 7. 阻礙與待辦

1. **MLX 訓練的 Metal Internal Error：** bf16 底座約每 300 iter（10–25 分鐘）會出現一次，降 seq 和設 cache limit 都沒有解決。可能的做法：外層自動 resume 迴圈（`m6_mlx_lora_run.py` 已支援從最新檢查點接續）、升級 macOS／MLX。
2. **token 數不足：** 只用了 18.1 萬 tokens，目標是 0.5–1M。
3. **resume 的檔名問題：** resume 後 mlx_lm 的檢查點編號會從 1 重新開始，會覆蓋舊檔名。已手動改名為 `global0000400_adapters.safetensors`，下一版 wrapper 應該加上 offset。
4. **思考無法真正關閉：** 需要對話 SFT。另外，PPL 評測的 wikitext 和 LoRA 訓練資料同領域，PPL 下降不代表對話能力提升。
5. **速度量測受背景程式干擾：** 正式的 flash 驗收需要在乾淨系統上重新量測。

## 勘誤（2026-10-18，M7 發現）

本文所有「思考關」的結論都**無效**，包括「E2B QAT 檢查點實際上沒辦法關閉思考」、思考關的指令 3–4/15，以及推理外洩的觀察。原因有兩個：

1. mlx_lm 0.32 在沒有傳參數時會預設 `enable_thinking=True`，所以第一版 chat eval 其實是思考開。
2. 修正版預填的空 thought 區塊是 12B 以上的格式，E2B 不適用。

用正確格式重測（見 `07_nothink_M7.md`）的結果：

- 三個模型思考關都是 50/50 遵從，指令 14/15。
- 官方模型首個答案 token 為 0.043 秒，總時間 median 為 1.09 秒。

「思考開」和 PPL 的結果不受影響。「flash 槓桿」的首選因此改為**正確關閉思考**，思考上限 128 則降為思考開時才用得到的槓桿。
